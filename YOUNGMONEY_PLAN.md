## Learning Hub

The Financial Education Library will contain 12 dedicated article pages. Each of the six topics will have one beginner article and one experienced article. Every article will be no more than 500 words.

### Planned Article Pages

| Topic | Beginner page | Experienced page |
| --- | --- | --- |
| Credit | Credit: Your Borrowing Report Card | Credit: Read the Whole Profile, Not One Score |
| Budgeting | Budgeting: Give Every Dollar a Job | Budgeting: Build a Resilient Cash-Flow System |
| Investing | Investing: Start With Goals, Time, and Risk | Investing: Allocation, Costs, and Rebalancing |
| Debt | Debt: Make a Repayment Map | Debt: Compare the Real Cost of Repayment Options |
| Taxes | Taxes: Understand Your Paycheck and Return | Taxes: Plan for Income Beyond a Paycheck |
| Credit cards and rewards | Credit Cards: Make Rewards Secondary | Rewards: Calculate Net Value, Not Points |

### Page Requirements

- Each article has its own page and stable URL.
- Each page identifies its topic and experience level.
- Each article contains a short introduction, core concepts, a practical action, a key takeaway, and authoritative sources.
- The Learning Hub index links to all 12 pages and supports filtering by topic and experience level.
- Article pages include a clear path back to the Learning Hub.
- Content is educational and does not present individualized financial, investment, tax, or legal advice.

### Frontend Ownership Boundary

Learning Hub implementation will stay inside `client/src/features/learningHub/`. It will expose the page components and route metadata through a single entry point. Shared application routing, navigation, `App.jsx`, and global styles will not be changed without coordination with the frontend owner.

## Database Schema

### Financial Goals Persistence Plan

#### Schema interpretation

The implementation will follow `youngmoney_schema/youngmoney_db_schema_1.png`:

- `goal` is a lookup table of supported financial-goal types. Its initial rows are
  `Debt free`, `Purchase`, and `Savings`, matching the diagram's User app note.
- `user_goal` is the user-owned financial goal. It relates one authenticated user
  to one goal type and stores `name`, `target`, and `notes`.
- `notes` is optional in both the API and form (`blank=True`, `default=""`).
- The existing `accounts.User` model remains the user table. Its current primary
  key is a Django `BigAutoField`, so the foreign key must use that real type even
  though the draft diagram labels `users.id` as UUID.
- Use a UUID primary key for `UserGoal`, as shown in the diagram. Use
  `DecimalField(max_digits=12, decimal_places=2)` for `target` so currency values
  are exact; this is a deliberate refinement of the diagram's `bigint` target.

The existing onboarding selection (`travel`, `cashback`, `points`, and `build
credit`) is a credit-card optimization preference, not the diagram's financial
goal. It should remain a separate concept rather than being stored in
`user_goal`.

#### 1. Create the Django app and models

- Create a `goals` app under `server/goals/` and add `goals` to
  `INSTALLED_APPS`.
- Add `Goal` with `goal = CharField(max_length=100, unique=True)`.
- Add `UserGoal` with:
  - UUID `id` generated by the server.
  - `user = ForeignKey(settings.AUTH_USER_MODEL, related_name="goals",
    on_delete=CASCADE)`.
  - `goal = ForeignKey(Goal, related_name="user_goals", on_delete=PROTECT)` so
    a referenced lookup value cannot be accidentally deleted.
  - Required `name = CharField(max_length=150)`.
  - Required positive `target = DecimalField(max_digits=12, decimal_places=2)`.
  - Optional `notes = TextField(blank=True, default="")`.
- Register both models in Django admin.
- Generate an initial schema migration and a data migration that seeds the three
  supported goal types. The seed migration should use `get_or_create` so it is
  safe across environments.

#### 2. Add the authenticated REST API

- Add serializers for the goal lookup and user goal. Return the goal's ID and
  display label; accept its ID on writes.
- Validate that `target` is greater than zero, trim `name`, reject a blank name,
  and allow omitted, empty, or blank notes.
- Add these JWT-protected endpoints:
  - `GET /api/goals/types/` lists the seeded goal choices.
  - `GET /api/goals/` lists only `request.user`'s goals.
  - `POST /api/goals/` creates a goal owned by `request.user`; the client must
    not be allowed to submit or override `user_id`.
  - `GET`, `PATCH`, and `DELETE /api/goals/<uuid>/` operate only on a goal owned
    by `request.user` and return 404 for another user's UUID.
- Mount `goals.urls` from `youngmoney.urls` at `api/goals/`.

Example create request:

```json
{
  "goal": 2,
  "name": "First car",
  "target": "12000.00",
  "notes": "Aim to buy before next summer"
}
```

#### 3. Build and connect the financial-goal inputs

- Add a goals service in `client/src/services/goals.js` using the shared Axios
  client so JWT attachment and refresh continue to work.
- Build a financial-goal form with these inputs:
  - Goal type: required select populated by `GET /api/goals/types/`.
  - Goal name: required text input.
  - Target amount: required number input with `min="0.01"` and `step="0.01"`.
  - Notes: optional textarea, visibly labeled "Optional" and sent as an empty
    string when unused.
- Disable duplicate submits while saving, show field-level API validation errors,
  preserve entered values after a failed request, and show a success state only
  after the POST response confirms database persistence.
- Put the page behind `PrivateRoute`. Do not rely on `localStorage` as the source
  of truth for financial goals.
- After creation, display the returned goal or navigate to a goals list/dashboard
  that fetches from `GET /api/goals/`. Replace hard-coded goal data in the
  dashboard only when that integration is in scope.

#### 4. Test the persistence and ownership boundaries

- Model tests: relationships, optional notes, positive target validation, UUID
  creation, protected goal types, and cascade behavior when a user is deleted.
- Migration/seed test: the three lookup rows exist and are unique.
- API tests: authentication required; create with and without notes; invalid or
  non-positive target rejected; list is user-scoped; retrieve/update/delete work;
  and cross-user access returns 404.
- Frontend tests: required inputs, optional notes, loading and error states,
  correct POST body, and navigation/rendering after a successful response.
- Manual database check: create a goal through the UI, restart the backend, sign
  back in, and verify the goal is returned from the API rather than local storage.

#### Definition of done

- A signed-in user can create a `Debt free`, `Purchase`, or `Savings` goal with a
  name and positive target; notes may be omitted.
- The record exists in PostgreSQL and remains available in a later session.
- Users can never view or mutate another user's goals.
- Migrations apply cleanly on an empty database, automated backend/frontend tests
  pass, and the API contract is documented with an example request and response.
